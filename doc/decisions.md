# 設計判断の記録

このドキュメントは `locale_sheet` で下した設計判断と、その理由・**採用しなかった案**を記録します。

## なぜ記録するか

コードと要件定義（[requirements.md](./requirements.md)）は「今どうなっているか」を示しますが、「なぜそうしたか」「他に何を検討して、なぜ採らなかったか」は残りません。その結果、次のような無駄が起きます。

- 一度却下した案が、時間をおいて再提案される
- 意図的な制約が「バグ」と誤認されて修正される
- 別のセッションや別の担当者が同じ調査をやり直す

各判断には ID（`ADR-xx`）を振ります。PR やコードコメントから `ADR-03` のように参照してください。

## 書き方

新しい判断は末尾に追記します。ID は再利用しません（過去の参照が壊れるため）。

各項目には次を含めます。

- **状況** — どういう問題に直面したか
- **判断** — 何を決めたか
- **理由** — なぜそれを選んだか
- **採用しなかった案** — 他に何を検討し、なぜ却下したか（これが本書の中心）
- **影響** — 判断の結果として受け入れた制約や副作用

判断を覆す場合は、既存の項目を書き換えるのではなく、新しい ID で追記し、古い項目に「`ADR-xx` により置き換え」と追記します。

## ADR-01: ロケール列の自動判定は緩いまま維持し、明示指定を用意する

**状況**

ロケール列の判定 `isValidLocaleTag` は言語サブタグを「英字2〜8文字」で判定するため、`memo` `note` `comment` `context` `status` `owner` `id` `screen` `category` といった一般的な列名がすべてロケールとして採用されていた。`key | en | ja | memo` というシートから `app_memo.arb` が生成される。`description` が除外されるのは11文字で長さ制限に引っかかるためであり、意図した除外ではない。

**判断**

判定ロジック自体は変更せず、`--locales`（ライブラリでは `locales` 引数）による明示指定を追加した。指定が無い場合は従来どおりの自動判定。どちらの場合も、ロケールとして採用した列と無視した列の両方を常にログに出力する。

**理由**

既定の挙動を変えないため、既存利用者のシートが突然エラーになったり出力が変わったりしない。必要な利用者だけが明示指定に移行できる。判定が緩いことによる事故は、採用結果を常に見せることで気付けるようにした。

**採用しなかった案**

- **ISO 639 の言語コード集合と照合して厳格化する** — `qq` のような私用コードや、将来追加される言語コードを弾いてしまう。コード表をパッケージに同梱・保守する負担も生じる。
- **ロケール判定を諦めて明示指定を必須にする** — 既存利用者全員に影響する破壊的変更であり、単純なシートでの手軽さも失われる。

**影響**

自動判定の緩さは仕様として残る。要件定義では FR-12a と第8章の既知の制限に明記した。README にも「自動判定は緩い」ことを注意として記載している。

参照: [PR #41](https://github.com/willow-c/locale_sheet/pull/41)

## ADR-02: 同一ロケールを指す列はエラーにする

**状況**

`zh-TW` と `zh_TW`、あるいは `en` と `EN` は BCP 47 では同一のロケールを指すが、それぞれ別のロケール列として扱われ、同じ ARB ファイル名に書き出されて後の列が先の列を黙って上書きしていた。大文字小文字違いに至っては、大文字小文字を区別しないファイルシステム（Windows / macOS）では1ファイル、区別するファイルシステム（Linux）では2ファイルとなり、同じ入力から異なる出力が出ていた。

**判断**

正規化キー（`trim` + 小文字化 + `_`→`-`）が一致する複数のロケール列を `FormatException` とする。検出はパーサとエクスポータの2箇所に置く。

**理由**

列がまるごと失われる事故であり、警告では弱い。パーサに置くことで「どの列とどの列が衝突したか」を示せる。エクスポータにも置くのは、利用者が `LocalizationSheet` を直接組み立てる経路をパーサ側の検査では守れないため。ファイル名の衝突は本質的に出力層の関心事でもあり、将来のエクスポータでも同じ検査が要る。

**採用しなかった案**

- **列をマージする** — `zh-TW` と `zh_TW` を同一ロケールとみなして統合する案。セル単位でどちらを優先するかが曖昧で、結局「黙って一方が消える」という元の問題と同じ性質になる。
- **警告に留める** — 重複キー（ADR-03）は警告に留めたが、あちらは出力自体は概ね正しい。こちらは列がまるごと消えるため深刻度が異なる。

**影響**

これまで（誤った結果ながら）成功していた入力がエラーになる、意図した破壊的変更。`en` と `EN` を別ロケールとして使い分ける運用は禁止される。

参照: [PR #42](https://github.com/willow-c/locale_sheet/pull/42)

## ADR-03: 重複キーは警告に留め、エラーにしない

**状況**

同じキーが複数行にある場合、解析は成功し、エクスポート時にロケールごとに独立して後の行が優先される。空セルは上書きしないため、行によって空セルの位置が違うと `en` は後の行・`ja` は前の行という食い違った出力になり得る。

**判断**

パース結果から重複キーを取得できるようにし（`LocalizationSheet.duplicateKeys`）、CLI は該当キーごとに警告を出す。終了コードは変えず、処理は継続する。

**理由**

重複があっても出力される ARB は概ね妥当であり、既存の利用者のビルドを止めるべきではない。一方で気付けないのは問題なので、警告で可視化する。

**採用しなかった案**

- **エラーにする** — 既存利用者のパイプラインを壊す。重複が意図的（後の行で上書きする運用）である可能性も否定できない。
- **後の行で完全に置き換える** — 現在の「ロケールごとに独立して後勝ち」を「行単位で後勝ち」に変える案。挙動としては一貫するが、既存の出力が変わる破壊的変更になる。

**影響**

食い違った出力が生成される可能性は残る。要件定義の第8章に既知の制限として明記している。

参照: [PR #34](https://github.com/willow-c/locale_sheet/pull/34)

## ADR-04: テストはメモリ生成を主とし、実ファイルの e2e は少数に絞る

**状況**

全テストが `Excel.createExcel()` でメモリ上に組み立てたワークブックを使っており、実際の表計算ソフトが書き出したファイル（共有文字列を参照する形式）の解析経路が一度も検証されていなかった。配布している `example/sample.xlsx` もどのテストからも読まれていなかった。

**判断**

ケース網羅（ヘッダ異常、空行、ロケール判定、重複キーなど）は従来どおりメモリ生成で行う。実ファイル経路の担保は `example/sample.xlsx` を使った少数の e2e テストに任せ、生成された ARB を全文一致で検証する。

**理由**

同梱サンプルは説明列・プレースホルダ・5ロケール・2シートを備えており、1ファイルで主要経路をほぼ通せる。副次的に、配布サンプル自体の回帰と `example/README.md` の表との整合も検出できる。

**採用しなかった案**

- **ケースごとに `.xlsx` fixture を用意する** — バイナリが増えると PR で期待値の変更が読めなくなり、更新のたびに表計算ソフトを開く必要がある。CI で再生成もできない。`example/*.xlsx` は Git LFS 管理（`.gitattributes`）でもある。

**影響**

`example/sample.xlsx` を変更する際は e2e テストの期待値も更新が必要になる。これは意図した結合であり、サンプル変更が無検証で通らなくなる。

参照: [PR #40](https://github.com/willow-c/locale_sheet/pull/40)

## ADR-05: 到達不能な防御的コードは、テストで無理に到達させない

**状況**

カバレッジを詰める過程で、公開 API 経由では到達できない分岐が残った。

- `parser.dart` のシート0件時の分岐 — `excel` パッケージは最後のシートの削除を拒否するため、シートを持たない `Excel` を構築できない。`Excel.decodeBytes` も有効な xlsx なら必ず1つ以上のシートを返す。
- `export_runner.dart` の `_emitError` の3番目の分岐 — `_buildEffectiveLogger` は「ロガー自身」か「ロガーが `SimpleLogger` のときに限り新しい `SimpleLogger`」しか返さないため、先行する2条件のいずれかに必ず一致する。

**判断**

到達させるために実装を歪めたり、リフレクション等で無理に到達させたりしない。防御的コードとして残し、到達不能である理由を記録する。

**理由**

カバレッジは目的ではなく手段。到達のためだけに公開 API を広げたりテスト専用の抜け道を作ったりすると、設計が悪くなる。将来 `_buildEffectiveLogger` の実装が変われば `_emitError` の分岐は意味を持つため、削除もしない。

**採用しなかった案**

- **該当コードを削除する** — 前提が変わったときの安全網を失う。
- **カバレッジ計測から除外する（`// coverage:ignore`）** — 除外指定が増えると、本当に検証すべき箇所の見落としと区別できなくなる。

**影響**

行カバレッジは 100% にならない（現状 99% 程度）。未到達行とその理由は PR に記録している。

参照: [PR #40](https://github.com/willow-c/locale_sheet/pull/40)

## ADR-06: CHANGELOG は利用者向けに限定する

**状況**

`CHANGELOG.md` は pub.dev の Changelog タブに表示される利用者向けの文書だが、`AGENTS.md` の書き換え、`CLAUDE.md` の追加、`doc/requirements.md` の新設、`.claude/settings.json` の追加といったリポジトリ内部の変更まで記載されていた。

**判断**

利用者に影響する変更のみを記載する。記載する／しないの基準と、迷った場合の判断基準「この行を読んだ利用者が、自分のコードや使い方を変える必要があるか」を [AGENTS.md](../AGENTS.md) の「ドキュメントと履歴管理」に明文化した。

**理由**

内部変更が並ぶと、本当に確認すべき仕様変更が埋もれる。

**採用しなかった案**

- **内部変更用のセクションを別に設ける** — pub.dev には CHANGELOG 全体が表示されるため、セクションを分けても利用者の目には入る。

**影響**

内部変更のみの PR では CHANGELOG を変更しない。PR テンプレートのチェック項目もそれに合わせている。

参照: [PR #38](https://github.com/willow-c/locale_sheet/pull/38)

## ADR-07: 公開アーカイブは利用者に必要なものだけに絞る

**状況**

`dart pub publish` の既定はドット始まりと ignore 対象を除く全ファイルを含める。そのため `AGENTS.md` `CLAUDE.md` `doc/` `test/` `scripts/` `Makefile` `analysis_options.yaml` がすべて公開されていた。

**判断**

`.pubignore` でこれらを除外し、`pubspec.yaml` / `LICENSE` / `README` / `CHANGELOG` / `example/` / `lib/` / `bin/` に絞る。`example/` は使い方サンプルとして公開を維持する。

**理由**

pub.dev のスコアが要求するのは上記のファイル群であり、それ以外は利用者に使われない。pub.dev はテストを実行しない（スコアリングは `pana` による静的解析のみ）ため `test/` を同梱する意味がない。`analysis_options.yaml` も pana が自前の設定を用意するため不要で、同梱すると `very_good_analysis` の厳格なルールが pub.dev 側の解析に上乗せされ、ルール追加でスコアが下がる余地が生まれる。

**採用しなかった案**

- **既定のまま全部公開する** — 一般的ではあるが、それは多くのパッケージが絞り込みをしていないだけで、推奨されているわけではない。

**影響**

`.pubignore` は同ディレクトリの `.gitignore` を**置き換える**仕様のため、`.gitignore` の内容を複製している。`.gitignore` に除外を追加する際は `.pubignore` の前半も併せて更新する必要がある。ファイル冒頭にその旨を記載している。

参照: [PR #38](https://github.com/willow-c/locale_sheet/pull/38), [PR #39](https://github.com/willow-c/locale_sheet/pull/39)

## ADR-08: エージェント運用ドキュメントはツール非依存にする

**状況**

`AGENTS.md` が「変更はパッチ（diff）形式で提出する」「PR に patch を添付する」「`apply_patch` の利用例」といった、パッチ添付を前提とした運用で書かれていた。ファイルを直接編集して PR を出す実際の運用と乖離していた。

**判断**

`AGENTS.md` を唯一の規約ソースとし、ツール非依存に保つ。ツールごとの読み込み口となるファイル（Claude Code の `CLAUDE.md` など）は `AGENTS.md` を参照するだけに留め、規約そのものを複製しない。

**理由**

規約を複製すると二重管理になり、どちらかが古くなる。ツールを乗り換えるたびに規約を書き直す必要もなくなる。

**採用しなかった案**

- **ツールごとに規約を書く** — 内容が重複し、更新漏れが必ず起きる。

**影響**

`CLAUDE.md` は `@AGENTS.md` による取り込みと、コマンド早見表などのツール固有の補足だけを持つ薄いファイルになっている。

参照: [PR #34](https://github.com/willow-c/locale_sheet/pull/34)

## ADR-09: ロケール列が1つも無い場合はエラーにする

**状況**

ロケール列が1つも無いシート（`key` 列しか無い、あるいはどの列もロケールとして採用されなかった）を変換すると、エクスポータは何も書き出さないにもかかわらず、CLI は終了コード `0` と `Result: Success` を報告していた。ヘッダ行を間違えた利用者が、出力が空であることに気付けない。

**判断**

CLI（`ExportRunner`）でロケール列が空であることを検出し、終了コード `64` でエラーとする。エラーメッセージには無視した列の一覧と `--locales` による回避策を含める。

**理由**

「1ファイルも生成していないのに成功と報告する」のは、CLI として明確に誤り。検査を CLI 層に置いたのは、コアのモデルとしては「ロケールを持たないシート」は表現可能であってよく、ライブラリ利用者がそのような `LocalizationSheet` を組み立てることを禁じる理由が無いため。成功／失敗を人間に報告する層だけが、この状態を拒否すればよい。

終了コードに `64` を選んだのは、既存の「指定シートが存在しない」「指定したデフォルトロケールがシートに無い」と同じ「入力に必要なものが揃っていない」種類のエラーであり、コードベースが既にそれらを `64` としているため。

**採用しなかった案**

- **パーサでエラーにする** — コアが「ロケール0件のシート」を表現できなくなる。また行数0のシートを正常に空の結果として返す既存仕様（FR-06）と矛盾する。
- **警告に留める** — 出力が空であることは警告で流せる程度の問題ではない。CI に組み込んでいる利用者は終了コードしか見ないため、成功のまま通ってしまう。
- **終了コード `65`（EX_DATAERR）を新設する** — 意味としては近いが、コードベースは `0` / `1` / `64` の3つで運用しており、区分を増やす利得が小さい。

**影響**

これまで成功していた入力がエラーになる破壊的変更。ただし出力は元から空であり、成功と報告されていたこと自体が問題だったため、実害のある互換性の破壊ではない。ライブラリ経由では従来どおりロケール0件のシートを扱える。

参照: [PR #44](https://github.com/willow-c/locale_sheet/pull/44)

## ADR-10: 深刻度はログレベルで表し、メッセージ本文に埋め込まない

**状況**

`Logger` には情報とエラーの2レベルしか無く、警告は `info('WARNING: ...')` という文字列の接頭辞で表現されていた。重複キー、未宣言プレースホルダ、無効になるオプションの3種類の警告がすべてこの形になっており、呼び出し側が深刻度でフィルタできなかった。警告が標準出力に混ざるため、標準出力をリダイレクトすると見えなくなる問題もあった。

**判断**

`Logger` に `warn` レベルを追加する。`SimpleLogger` は警告を標準エラー出力へ黄色で書き、`WARNING:` の接頭辞はレベル側が付与する。呼び出し側はメッセージ本文に深刻度を書かない。

**理由**

深刻度がメッセージ本文にあると、機械的な判別ができず、接頭辞の書き忘れや表記ゆれも防げない。警告を標準エラー出力に送るのは CLI の慣行であり、標準出力をリダイレクトしても警告が見える。

**採用しなかった案**

- **警告も標準出力のままにする** — 従来と互換だが、標準出力をリダイレクトすると警告が失われる。本 CLI の成果物はファイルであり標準出力ではないため、標準出力を保つ利点が小さい。
- **`Logger` を変えず、呼び出し側で接頭辞を統一する規約にする** — 規約は破られる。型で表現できるものを規約に落とす理由が無い。

**影響**

`Logger` インターフェースにメソッドが増えるため、これを実装している既存コードは破壊的変更となる（`Logger` は公開バレルから export されていないため、影響範囲は限定的）。警告の出力先が標準出力から標準エラー出力に変わるため、標準出力を grep して警告を拾っていた利用者は影響を受ける。

なお `Logger` インターフェースが CLI の特定出力に密結合している問題（`infoSheetLocales` など6メソッド）は本 ADR では扱っていない。インターフェースの整理は別途行う。

参照: [PR #45](https://github.com/willow-c/locale_sheet/pull/45)

## ADR-11: プレースホルダ解決をコアに置き、シートは書き換えず作り直す

**状況**

プレースホルダの自動検出が `ExportRunner.run` の中に4重ネストで実装されていた（エントリ → ロケール → 検出結果 → 扱いの分岐）。`run` は180行に達し、検出・付与というドメインロジックが CLI 層にあった。さらに `sheet.entries[ei] = newEntry` でモデルのリストを直接書き換えており、`LocalizationEntry` が不変であることと矛盾していた。

**判断**

検出と付与を `lib/src/core/placeholder_resolver.dart` の `PlaceholderResolver` に切り出す。解決器は入力のシートを変更せず、新しいシートと「宣言されていなかったプレースホルダの一覧」を返す。あわせて `LocalizationSheet` が保持するリストを変更不可にする。

検出結果をどう扱うか（警告する・無視する・エラーにして終了コードを返す）は CLI の判断として残す。

**理由**

ログ出力や終了コードは表示・制御の関心事であり、コアに持ち込むと再利用できなくなる。逆に「どのメッセージにどのプレースホルダがあり、どれが未宣言か」は純粋な計算であり、コアに置けば副作用なくテストできる。

リストを変更不可にしたのは、1箇所の書き換えを直すだけでは再発するため。型で禁止すれば、将来同じ書き方をしようとした時点でコンパイルエラーになる。

**採用しなかった案**

- **解決器に扱いの方針（warn / ignore / add / error）をそのまま渡す** — コアがログ出力や中断の責務を持つことになる。`add` するかどうかだけを真偽値で受け取り、報告は呼び出し側に任せる形にした。
- **`LocalizationSheet` に `copyWith` を足して書き換えを続ける** — 呼び出し側が書き換えを選べる状態が残る。リスト自体を変更不可にするほうが確実。
- **`ExportRunner.run` の分割だけ行い、ロジックは CLI に残す** — 行数は減るが、ドメインロジックが CLI にある問題は解決しない。

**影響**

`LocalizationSheet` のリストが変更不可になるため、取得したリストを書き換えていたコードは実行時エラーになる（本リポジトリ内には該当なし）。`PlaceholderResolver` と `PlaceholderFinding` は公開 API として export した。

`error` の扱いに1点だけ違いがある。従来は最初の未宣言を見つけた時点で走査を打ち切っていたが、現在は全件を集めてから最初の1件を報告する。報告内容と終了コードは同じで、余分に走査するだけ。

参照: [PR #46](https://github.com/willow-c/locale_sheet/pull/46)

## ADR-12: オプションの参照は定義の有無を確認し、例外を握り潰さない

**状況**

`ExportRunner.run` の中に、`ArgResults` からオプションを読むためのクロージャが2つあり、どちらも `on Object catch (_)` で全例外を握り潰していた。

```dart
T? getOption<T>(String name) {
  try {
    return argResults[name] as T?;
  } on Object catch (_) {
    return null;
  }
}
```

これは、テストが一部のオプションだけを定義した縮小版の `ArgParser` を使うためで、未定義のオプションを読むと `ArgResults` が例外を投げることへの対処だった。しかし全例外を捕まえるため、オプション名の綴り間違いも黙って既定値に落ちる。

**判断**

`ArgResults.options` に名前が含まれるかを確認してから読む。例外処理はやめる。あわせて `ExportRunner` が「オプションが定義されていない `ArgResults`」を受け付けること自体を、意図された契約としてテストで明示する。

**理由**

未定義のオプションを読もうとしているのか、値の型が想定と違うのか、といった区別が例外の握り潰しでは失われる。定義の有無は `options` で直接問い合わせられるため、例外に頼る理由が無い。

縮小パーサを許容する仕様自体は維持した。`ExportRunner` は `ExportCommand` 以外からも使えるようにしてあり、呼び出し側が必要なオプションだけを定義できるほうが扱いやすいため。ただし従来はそれが「例外を握り潰した副作用」として暗黙に成立していたので、テストで契約として固定した。

**採用しなかった案**

- **`ExportCommand` の `ArgParser` を必須とし、縮小パーサを許容しない** — `ExportRunner` を単体で使う際の柔軟性が失われる。テストも毎回すべてのオプションを定義する必要がある。
- **未定義のオプションを読んだら例外を投げるままにする** — 呼び出し側にすべてのオプション定義を強制することになり、上と同じ問題。

**影響**

外部から観測できる挙動は変わらない。`run()` は 158行から58行になった（`_prepareSheet` と `_warnIfTreatOptionHasNoEffect` への分割を含む）。

契約をテストで固定したことで、`_logHeaderAndOptions` と `_determineDefaultLocale` が `argResults` を直接参照したままだったことが判明した。従来はテスト用パーサがたまたまそれらのオプションを定義していたため露見していなかった。縮小パーサの許容は「例外を握り潰していたから偶然動いていた」状態であり、実際には一部の経路で成立していなかった。

参照: [PR #47](https://github.com/willow-c/locale_sheet/pull/47)

## ADR-13: セル値の文字列化は型ごとに明示し、`toString()` に依存しない

**状況**

`ExcelParser._cellToString` はセル値を `value.toString()` で文字列化していた。`toString()` は表示・デバッグ用の表現であって安定した契約ではないため、`excel` パッケージを更新すると生成される ARB の内容が黙って変わり得る。実際に確認したところ、日付セルは `2026-07-28T00:00:00.000Z`、時刻セルは `09:05:03`、数式セルは数式そのものが出力されていた。

**判断**

`CellValue` が sealed class であることを利用し、型ごとに変換を明示する `switch` に置き換える。出力される文字列は従来と同一に保つ。

**理由**

sealed class に対する `switch` は網羅性が検査される。将来のバージョンでセル型が追加された場合、暗黙に別の文字列が出るのではなく**コンパイルエラー**になる。依存パッケージの変更を、実行時の静かな挙動変化ではなくビルド時の失敗として受け取れる。

`TextCellValue` だけは `value.toString()` を残した。`TextSpan.toString()` は装飾付きテキストを平坦化して連結する処理であり、デバッグ表現ではない。子スパンを含めた本文を得る公開手段が他に無く、自前で再実装すると本家の処理と乖離する危険がある。この判断はコメントとして実装に残した。

**採用しなかった案**

- **`is` による分岐を並べる** — 網羅性が検査されないため、型が追加されても気付けない。`toString()` 依存と同じ問題が残る。
- **この機会に日付・時刻の表記を改める** — 日付セルの `2026-07-28T00:00:00.000Z` は、日付に時刻とタイムゾーンが付いており不自然。ただし表記の変更は既存利用者の出力が変わる別種の判断であり、本 ADR の目的（依存の不安定さの解消）とは分けるべきと考えた。従来の出力を維持し、変更は将来の判断に委ねる。

**影響**

外部から観測できる挙動は変わらない。全8種のセル型について、変換結果を固定するテストを追加した。

参照: [PR #48](https://github.com/willow-c/locale_sheet/pull/48)

## ADR-14: ワークブックのデコードは1回にし、解析結果がシート名も報告する

**状況**

CLI は1回の実行でワークブックを2回デコードしていた。1回目は `getSheetNames` でシート一覧をログに出すため、2回目は `parse` で実際に解析するため。同じバイト列を2回展開しており、大きなファイルほど無駄が大きい。

加えて、シート名を省略した場合に「実際にどのシートを解析したか」を CLI 側が `sheetListResult.sheets.first` で推測し直していた。解析器の判断を別の場所で再現する形になっており、両者がずれる余地があった。

**判断**

`ExcelParser.parseWorkbook` を追加し、シートに加えて「実際に解析したシート名」と「含まれるシート名の一覧」を返す `ParsedWorkbook` を返す。CLI はこれ1回だけを呼ぶ。既存の `parse` は `parseWorkbook(...).sheet` を返す薄い包みとして残す。

**理由**

デコードは解析器の内部事情なので、必要な情報をまとめて返すのが自然。シート名を解析器が報告することで、CLI 側の推測が不要になり、ずれる余地が消える。

**採用しなかった案**

- **デコード結果を解析器がキャッシュする** — 同じバイト列かどうかの判定が必要になり、解析器が状態を持つ。テストでの差し替えも複雑になる。
- **`LocalizationSheet` にシート名の一覧を持たせる** — シート名はワークブック単位の情報であり、1枚のシートを表すモデルに混ぜるのは筋が悪い。
- **`getSheetNames` を削除する** — シート名だけを知りたい利用者には有用なので公開 API として残した。ただし解析も行う場合は `parseWorkbook` を使うよう、ドキュメントコメントで案内している。

**影響**

`ExcelParser` を継承して `parse` を差し替えていたコードは、`parseWorkbook` を差し替える必要がある（本リポジトリ内のテストフェイク6箇所を更新した）。

`(failed to list sheets)` と `(workbook has no sheets)` というログ表現は消滅した。前者は「シート一覧の取得だけが失敗し解析は成功する」、後者は「シートが0枚なのに解析が成功する」状態を表すもので、デコードが1回になった今はどちらも起こり得ない。これらを検証していた2件のテストは、フェイクでしか作れない状態を確かめていたため削除し、解析器が報告したシート名がログに使われることを検証するテストに置き換えた。

シート一覧のログは解析成功後に出るようになった。解析に失敗した場合は表示されないが、`SheetNotFoundException` のメッセージが利用可能なシート名を含むため情報は失われない。

参照: [PR #49](https://github.com/willow-c/locale_sheet/pull/49)

## ADR-15: 責務ごとにファイルを分け、`mapHash` の並べ替えをやめる

**状況**

`model_helpers.dart` に、汎用の Map ユーティリティ（`mapEquals` / `mapHash`）とロケールタグの判定（`normalizeLocaleTag` / `isValidLocaleTag` / `isSafeArbLocaleTag`）が同居していた。前者はモデルの等価比較のための道具、後者はこのパッケージのドメイン規則であり、まったく別の関心事。ファイル名の「helpers」も、何が入っているかを説明していない。

また `mapHash` は排他的論理和でハッシュを合成しているにもかかわらず、毎回キーを並べ替えていた。排他的論理和は順序に依存しないため無意味な処理であり、さらに `Map<Object?, Object?>` を受けながら並べ替えるため、`Comparable` でないキーを渡すと実行時例外になる欠陥もあった。

**判断**

`locale_tag.dart`（ロケール規則）と `map_utils.dart`（Map ユーティリティ）に分割する。`mapHash` からは並べ替えを削除する。

**理由**

ファイル名が中身を説明し、変更の理由が1ファイルに1つ対応するようにする。`mapHash` の並べ替えは、削っても結果が変わらない（排他的論理和は交換法則を満たす）うえに、潜在的な実行時例外も消える。

**採用しなかった案**

- **`model_helpers.dart` の名前を残し、中でセクション分けする** — 名前が中身を説明しない問題が残り、片方だけを触りたい場合も同じファイルを開くことになる。
- **`mapHash` の並べ替えを残したまま、キーの型を `Comparable` に制約する** — 呼び出し側に不要な制約を課す。並べ替え自体が不要なので、制約を足すより削るほうが素直。

**影響**

`mapHash` の戻り値は変わらない（排他的論理和の結果は順序に依存しないため）。ファイルの移動は `git mv` で行い、履歴を保っている。ドキュメント4箇所の参照先を更新した。

参照: [PR #50](https://github.com/willow-c/locale_sheet/pull/50)

## ADR-16: `Logger` は公開せず、インターフェースの整理も保留する

**状況**

`Logger` には CLI の特定出力に密結合したメソッドが6つある（`infoOptions` / `infoAvailableSheets` / `infoSheetLocales` / `infoDefaultLocale` / `infoResult` / `infoErrorResult`）。カスタムロガーを実装する負担が大きく、設計としては `info` / `warn` / `error` に絞って整形はプレゼンタ層へ移すのが筋。

また `ExportCommand({Logger? logger})` は公開クラスのコンストラクタでありながら、`Logger` 型は公開バレルから export されていない。利用者は `package:locale_sheet/src/cli/logger.dart` を直接 import しない限りロガーを差し替えられない。

一方で本パッケージの主な使われ方は CLI であり、ライブラリとしての利用は多くないと見込んでいる。

**判断**

`Logger` を export せず、インターフェースの整理も現時点では行わない。この状態を意図的なものとして、`ExportCommand` と `ExportRunner` のドキュメンテーションコメントに明記する。

**理由**

コア（パーサ、モデル、エクスポーター、`PlaceholderResolver`）は `Logger` に一切依存しておらず、`Logger` が現れるのは `lib/src/cli/` の中だけ。ライブラリとしての入口である `convertExcelToArb` / `ExcelParser` / `ArbExporter` / `PlaceholderResolver` はロガーを受け取らない。つまり**ライブラリ利用の道は既に開いており、`Logger` を公開しなくても塞がらない**。

公開 API は追加は容易だが変更と削除は破壊的変更になる。いま export すると現在の8メソッドの形が固定され、後から整理しようとすると利用者のコードを壊す。export しなければ内部の継ぎ目のままなので、**いつ整理しても破壊的変更にならない**。

したがって先送りのコストはゼロで、いま実施すると整形処理の作り替えに伴うリグレッションのリスクだけを先払いすることになる。

**採用しなかった案**

- **いま `Logger` を export する（B-8 単体）** — 利用者が `src/` を直接 import する不便は解消されるが、整理前の形を公開 API として固定してしまう。順序が逆。
- **いまインターフェースを整理してから export する** — 設計としては最も筋が通るが、現在の色付けはメッセージ構造ごとに行われている（`Options:` はシアン、値はマゼンタ）ため、整形と色の責務をプレゼンタ層へ移す作業になる。`TestLogger` とテストの検証方法も広範囲に変わる。利用者不在の状態でこのリスクを取る理由が無い。

**見直しの条件**

出力を差し替えたい利用者が実際に現れたとき。その場合は **export の前にインターフェースを絞る**（`info` / `warn` / `error` の3つにし、整形はプレゼンタ層へ移す）。順序を逆にすると破壊的変更になる。

**影響**

`ExportCommand` の `logger` 引数は、公開クラスの引数でありながら公開 API ではないという状態が残る。ドキュメンテーションコメントで意図を明示し、ライブラリ利用時は CLI を経由せずコアを直接呼ぶよう案内した。

参照: [PR #51](https://github.com/willow-c/locale_sheet/pull/51)

## ADR-17: 検証は何も削除せず、削除は既知のパスに限定する

**状況**

`make verify` は先頭で `clean` を呼んでいた。その `clean` は次の処理を含んでいた。

```bash
find . -type d -name l10n -exec rm -rf {} +
find . -type f -name '*.arb' -delete
```

リポジトリ配下の `l10n` という名前のディレクトリと、すべての `.arb` ファイルを名前で全体検索して削除する。本パッケージの出力先は利用者が `--out` で自由に指定できるため、`./l10n` に出力していた開発者が「検証」のつもりで `make verify` を実行すると、作業結果を失う。

さらに `clean` は `fvm flutter clean` を実行していた。本パッケージは `pubspec.yaml` に `flutter:` セクションを持たない純粋な Dart パッケージであり、Flutter ツールの起動（CI ログでは `Building flutter tool...` から始まる依存解決）が毎回発生していた。

加えて CI は `fvm dart pub get` を実行した直後に `verify.sh` を呼び、その中の `clean` が `.dart_tool/` を削除していたため、解決結果が数秒で捨てられていた。`verify.sh` と `verify.ps1` で手順も揃っていなかった（`pub get` の有無）。

**判断**

- `verify` から `clean` の呼び出しを外す。検証は何も削除しない。
- `clean` の削除対象を既知のパス（`.dart_tool/` `build/` `coverage/` `lib/l10n/` `example/out/`）に限定し、名前による全体検索をやめる。
- `clean` から `flutter clean` を削除する。
- `verify.sh` / `verify.ps1` の手順を揃え、どちらも `pub get` から始める。CI 側の重複した `pub get` ステップは削除する。

**理由**

「verify」という名前から削除は予期できない。破壊的な操作は、利用者が明示的に選んだときにだけ起きるべき。

削除対象を名前で全体検索するのは、消してよいものを「名前が一致するかどうか」で判断していることになる。生成物の場所はこのリポジトリが決めているので、パスを直接指定すれば足りる。

`flutter clean` が消すのは `build/` と `.dart_tool/` であり、`rm -rf` で置き換えられる。Flutter に依存しないパッケージのために Flutter ツールを起動する理由が無い。

**採用しなかった案**

- **`verify` から `clean` を残したまま、削除対象だけ限定する** — 範囲は狭まるが「検証したら消える」性質は残る。生成物であっても、検証のたびに消える必要は無い。
- **CI 側だけ `clean` を呼ぶ** — CI は毎回まっさらなチェックアウトなので、そもそも不要。

**影響**

`make verify` の実行時間が短くなり（Flutter ツールの起動が無くなる）、実行しても作業ディレクトリのファイルが消えなくなる。まっさらな状態から検証したい場合は `make clean && make verify` と明示的に書く。

参照: [PR #52](https://github.com/willow-c/locale_sheet/pull/52)

## ADR-18: コマンド未指定は使い方の誤りとして扱う

**状況**

エントリポイントをプロセスとして起動するテストを書いたところ、**引数を1つも与えずに実行すると終了コードが `0`** になることが分かった。`CommandRunner.run([])` は使い方を標準出力に表示して `null` を返し、`main` は `null` を成功として扱っていたため。

呼び出し側のスクリプトが引数の組み立てに失敗して空になった場合、何も変換していないのに成功として通過する。

**判断**

引数が空の場合は使い方を**標準エラー出力**に表示し、終了コード `64` で終える。`--help` のようにヘルプを明示的に要求した場合は従来どおり `0`。

**理由**

「何も実行していないのに成功として終わらない」という原則は ADR-09（ロケール列0件をエラーにする）と同じ。呼び出し側は終了コードしか見ないため、そこで区別できなければ気付けない。

ヘルプの明示要求と、コマンドを書き忘れた状態は意味が違う。前者は求めたものが得られているので成功、後者は指示が不完全なので失敗。引数が空かどうかで両者を区別できる。

使い方を標準エラーに出すのは、これがエラー時の出力だから。ADR-10 で警告とエラーを標準エラーへ送ると決めた方針に揃えている。

**採用しなかった案**

- **ヘルプ表示として `0` のまま扱う** — 多くの CLI（`dart` 自身を含む）はコマンド未指定を使い方の誤りとして非ゼロで終える。何もしていないことを呼び出し側が検出できる必要がある。
- **`CommandRunner` の戻り値が `null` なら一律 `64`** — `--help` や `help` サブコマンドも `null` を返すため、正当な要求まで失敗扱いになる。

**影響**

引数なしで実行していたスクリプトがあれば失敗するようになる。ただしその実行は元から何も生成していない。

参照: [PR #53](https://github.com/willow-c/locale_sheet/pull/53)
